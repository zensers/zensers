# A-F 改进方案效果深度分析

**日期**: 2026-06-06
**基线**: 比亚迪报告（research_8c6675c2），8 个 agent，68 个数据点，16 处矛盾（23.5% 矛盾率）

---

## 一、当前系统的真实数据流（基于代码追踪）

```
Phase 1: 8 个 research/analysis agent 并行
  │  每个 agent 独立搜索 + 独立分析（同一批 data_points 全量发给每个 agent）
  │  输出：8 份独立的章节文本（无交叉校验）
  │
  ├─ engine.py:1317-1343 → MetricExtractor 从 data_points 提取 12 种指标
  │  → 写入 SharedMemory["_canonical_registry"]
  │  → 但此数据仅以 "建议优先使用" 形式注入 prompt，LLM 可忽略
  │
  ▼
Phase 2: 聚合 (result_aggregator.py:926-1121)
  │  冲突检测基于 agent_id 作为 key
  │  每个 agent 的 content 是完整文本（数千字），不是结构化指标
  │  冲突检测只能发现 "同一 agent_id 出现两次"，不能发现数据矛盾
  │
  ▼ 实际聚合逻辑：把 8 份文本原封不动放入 sections 列表
  │  → 无任何数据一致性校验
  │
  ▼
Phase 3: 文档生成
  │  document_generation_agent 直接拼接 sections
  │  无后处理扫描
  │
  ▼
输出：包含矛盾的最终报告
```

**核心问题定位**：矛盾数据从 agent 输出后就已成型，后续流程中**没有任何环节会检测或修正文本内的具体数据值**。

## 二、A-F 各方案的干预点与预期效果

### 方案 A：清理死数据 + 扩展 MetricExtractor

**干预点**：Phase 1 的数据提取层

**具体改动**：
1. 删除 generic_agent.py:321-352 的 `write_canonical()` 调用（死代码）
2. 在 MetricExtractor 中添加复合指标（ROE、净利率、资产负债率、PE、PB 等）

**对基线问题的效果**：

| 问题 | 当前状态 | 修复后 | 原因 |
|------|---------|--------|------|
| 2024 销量 380/425/460 万 | MetricExtractor 有销量正则 | **无改善** | 规范数据已有销量值，LLM 仍然忽略 |
| 毛利率 19.58/21.6/25% | MetricExtractor 有毛利率正则 | **无改善** | 同上 |
| 市占率 90% | MetricExtractor 有市占率正则 | **无改善** | 同上 |
| Prompt 泄漏 | - | **无改善** | 不相关 |
| 数据重复 | - | **无改善** | 不相关 |

**量化评估**：
- 矛盾率：23.5% → ~23.5%（几乎无改善）
- 原因：A 解决的是"有没有规范数据"，而当前问题不是缺少规范数据，而是规范数据对 LLM 无约束力
- **边际价值**：为后续方案提供更丰富的规范数据基础，但单独无效

### 方案 B：聚合阶段增加数据一致性校验

**干预点**：Phase 2 的聚合层

**关键发现**：当前 `result_aggregator.py` 的冲突检测**完全无法发现数据矛盾**。

原因分析（基于代码）：
```python
# result_aggregator.py:964-1077
# 1. 每个 agent_id 作为独立 key 存入 all_entries
all_entries[agent_id] = [(agent_id, actual_content, 0, stage)]
# actual_content 是数千字的完整文本

# 2. 冲突检测基于 key 碰撞
for key, entries in all_entries.items():
    if len(entries) == 1:
        merged_data[key] = entries[0][1]  # 每个 agent 唯一，永远不会触发冲突
    else:
        # 这里的冲突是"同一 key 有多个值"，但 key=agent_id，每个 agent 只出现一次
        ...
```

**结论：聚合器的冲突检测在当前架构下永远不会触发数据矛盾检测。**

**具体改动需求**：
1. 聚合时解析各章节文本中的数值指标（正则提取）
2. 按指标名+年份分组比对
3. 发现矛盾时自动裁决（取规范数据值或多数值）

**对基线问题的效果**：

| 问题 | 修复后 | 效果 |
|------|--------|------|
| 2024 销量 380/425/460 万 | 聚合时发现 4 个不同值 → 取规范数据值 | ✅ 根治 |
| 毛利率 19.58/21.6/25% | 聚合时发现 3 个不同值 → 取规范数据值 | ✅ 根治 |
| 市占率 90% | 聚合时发现 35% vs 90% → 标记矛盾 | ✅ 检测到 |
| Prompt 泄漏 | 不相关 | ❌ |
| 数据重复 | 不相关 | ❌ |

**量化评估**：
- 矛盾率：23.5% → ~5-8%（消除 70-80% 的数据矛盾）
- 限制：聚合时文本解析可能遗漏某些指标；口径差异需要人工规则
- **关键风险**：如果聚合阶段的裁决选择了错误值（如规范数据本身有误），会传播错误

### 方案 C：DataBus 集成为权威数据源

**干预点**：Phase 1 的数据查询层

**具体改动**：
1. 在 DataBus 中注册 AkshareProvider 作为权威财务数据源
2. Agent 在分析前先查询 DataBus 获取关键指标
3. 用 DataBus 返回的值覆盖搜索结果中的值

**对基线问题的效果**：

| 问题 | 修复后 | 效果 |
|------|--------|------|
| 2024 销量 | Agent 查询 Akshare 获取官方值 | ✅ 根治（如果数据源覆盖） |
| 毛利率 | Agent 查询 Akshare 获取官方值 | ⚠️ 部分改善（Akshare 可能无细分毛利率） |
| 市占率 90% | Akshare 无市占率数据 | ❌ 无改善 |
| Prompt 泄漏 | 不相关 | ❌ |
| 数据重复 | 不相关 | ❌ |

**量化评估**：
- 矛盾率：23.5% → ~15-18%（仅改善 DataBus 能覆盖的指标）
- **限制**：
  1. Akshare 仅覆盖 A 股上市公司财务数据，无法覆盖市占率、行业数据
  2. 高度依赖外部数据源可用性（Akshare API 可能不稳定）
  3. 实施复杂度高（需要重新设计 agent 查询链路）
- **边际价值**：对上市公司财务报告场景有效，但无法泛化到其他主题

### 方案 D：取消 content[:2000] 截断

**干预点**：Phase 1 的 agent 间数据传递

**具体改动**：
```python
# engine.py:1852 修改
"content": content[:2000],  # 当前
→

```

**对基线问题的效果**：

| 问题 | 修复后 | 效果 |
|------|--------|------|
| 2024 销量 380/425/460 万 | 后续 agent 能看到更多前序内容 | ⚠️ 微弱改善 |
| 毛利率 | 同上 | ⚠️ 微弱改善 |
| 市占率 90% | 同上 | ⚠️ 微弱改善 |
| Prompt 泄漏 | 不相关 | ❌ |
| 数据重复 | 后续 agent 能看到前序已写了什么 | ⚠️ 微弱改善 |

**量化评估**：
- 矛盾率：23.5% → ~20-22%（边际改善）
- **限制**：
  1. 更多上下文 ≠ 更好的一致性——agent 可能反而被矛盾信息混淆
  2. LLM 的注意力机制在长 prompt 中对数值的聚焦度下降
  3. 增加 token 消耗和延迟
- **边际价值**：对 synthesis agent 帮助较大，对并行 analysis agent 帮助有限

### 方案 E：强化 prompt 数据引用规范

**干预点**：Phase 1 的 LLM prompt 层

**具体改动**：
1. 将 "建议优先使用" 改为 "必须使用，否则标明出处"
2. 增加数据引用格式要求（必须标注 [规范数据] 或 [搜索结果]）
3. 增加 "不得编造数据" 的硬性指令

**对基线问题的效果**：

| 问题 | 修复后 | 效果 |
|------|--------|------|
| 2024 销量 | LLM 被要求必须用规范数据 | ⚠️ 概率性改善 |
| 毛利率 | 同上 | ⚠️ 概率性改善 |
| 市占率 90% | LLM 被要求不得编造 | ⚠️ 概率性改善 |
| Prompt 泄漏 | 增加 "不得暴露系统指令" | ⚠️ 部分改善 |
| 数据重复 | 不相关 | ❌ |

**量化评估**：
- 矛盾率：23.5% → ~15-18%（降低 ~25-30%）
- **限制**：
  1. LLM 对指令的合规率约 70-85%（基于业界经验），无法达到 100%
  2. 过于严格的指令可能降低分析质量（LLM 变得保守，不敢做推断）
  3. 不同模型（deepseek-v4-flash vs GPT-4）的合规率差异大
- **边际价值**：成本低、见效快，但天花板明显

### 方案 F：后处理扫描数据矛盾

**干预点**：Phase 3 的文档生成后

**具体改动**：
1. 扫描最终报告，正则提取所有数值
2. 按指标名+年份分组比对
3. 发现矛盾 → 用规范数据替换 + 标注置信度
4. 检测 prompt 泄漏模式并清除

**对基线问题的效果**：

| 问题 | 修复后 | 效果 |
|------|--------|------|
| 2024 销量 380/425/460 万 | 扫描发现矛盾 → 替换为统一值 | ✅ 根治 |
| 毛利率 19.58/21.6/25% | 扫描发现矛盾 → 替换为统一值 | ✅ 根治 |
| 市占率 90% | 扫描发现 90% vs 35% → 替换 | ✅ 根治 |
| Prompt 泄漏 | 正则匹配并清除泄露内容 | ✅ 根治 |
| 数据重复 | 不直接解决 | ❌ |

**量化评估**：
- 矛盾率：23.5% → ~3-5%（消除 80-85% 的数据矛盾 + 100% prompt 泄漏）
- **限制**：
  1. 正则替换可能破坏文本连贯性（上下文需要适配）
  2. 无法处理隐含矛盾（如 "大幅增长" vs "同比下降"）
  3. 如果规范数据本身有误，会传播错误
- **关键优势**：作为最终安全网，即使前面所有方案失败，F 也能兜底

## 三、A-F 组合效果的定量预估

### 叠加效应分析

各方案不是简单叠加，而是互为补充：

```
                    无修复       +E(强prompt)    +B(聚合校验)    +F(后处理)     全部A-F
                    ──────       ──────────     ──────────     ──────────    ──────────
数据矛盾率          23.5%        16-18%         8-10%          3-5%          2-3%
Prompt 泄漏         25%(2/8)     15-20%         25%            0%            0%
数据重复率          75%          70-75%         70-75%         70-75%        60-65%
───────────────────────────────────────────────────────────────────────────────────────
综合质量评分*       6/10         6.5/10         7.5/10         8/10          8.5/10
```

*综合质量评分：考虑数据准确性、文本连贯性、重复度、专业度

### 关键洞察

**B + F 组合是核心**：
- B 在聚合时发现矛盾（但可能破坏文本结构）
- F 在最终输出前统一替换（可以保持文本连贯性）
- 两者互补：B 早期拦截 + F 最终兜底

**A 是基础设施**：扩展 MetricExtractor 为 B 和 F 提供更丰富的规范数据

**E 是低成本增益**：prompt 强化不需要改代码结构，但边际效益递减

**C 的 ROI 最低**：高复杂度但仅对特定场景（上市公司财务数据）有效

**D 的效果最小**：2000 字符截断对数据一致性的影响被高估

## 四、A-F 无法解决的问题（盲区分析）

### 盲区 1：数据重复（75% 重复率）

**根因**：engine.py 把全部 data_points 全量发给每个 agent

```python
# engine.py:1890 (REPORT_GENERATION 路径)
"data_points": aggregated_data_points,  # 全量，无分配/去重
# engine.py:2095 (通用路径)
task["aggregated_data_points"] = deduped[:5000]  # 仅截断，非分配
```

**A-F 均不解决此问题**。需要在 engine 层面引入数据分配逻辑：
- 按 agent 的 aspect 过滤 data_points
- 或引入 "数据分工" 调度

### 盲区 2：LLM 编造数据的结构性风险

无论 prompt 多严格，LLM 仍有 ~5-15% 的概率：
- 编造不存在的数据点
- 将搜索结果中的数据错误解读
- 将不同年份的数据混淆

**A-F 无法将此概率降至 0**。这是生成式 AI 的结构性限制。

### 盲区 3：口径一致性的语义理解

"毛利率 19.58%" vs "毛利率 25%" 可能都是对的——一个是含少数股东口径，一个是不含。正则和规则引擎无法区分需要语义理解的口径差异。

## 五、实施优先级建议

### 第一梯队（必须实施，效果最大）

| 优先级 | 方案 | 预期矛盾率降幅 | 复杂度 |
|:------:|------|:-------------:|:------:|
| 1 | **F 后处理扫描** | 80-85% | 中 |
| 2 | **B 聚合校验** | 60-70% | 中 |
| 3 | **A 扩展 MetricExtractor** | 为 B/F 提供数据基础 | 低 |

**理由**：B+F 构成双层防线，A 提供规范数据支撑。三者组合可将矛盾率从 23.5% 降至 3-5%。

### 第二梯队（增强效果）

| 优先级 | 方案 | 预期矛盾率降幅 | 复杂度 |
|:------:|------|:-------------:|:------:|
| 4 | **E 强化 prompt** | 额外 5-10% | 低 |
| 5 | **D 去截断** | 额外 2-3% | 低 |

**理由**：边际效益递减，但实施成本低，值得一并推进。

### 第三梯队（长期投入）

| 优先级 | 方案 | 预期矛盾率降幅 | 复杂度 |
|:------:|------|:-------------:|:------:|
| 6 | **C DataBus 集成** | 仅特定场景有效 | 高 |

**理由**：ROI 低，建议放到后续迭代。

### 需要新增的方案

| 方案 | 解决的问题 | 复杂度 |
|------|-----------|:------:|
| **G: 数据分配调度** | 75% 重复率 | 中 |
| **H: 数据提取 Agent** | 结构化事实表，先于分析运行 | 中 |

**G 的设计**：在 engine.py 分发 data_points 时，按 agent 的 aspect 关键词过滤，避免所有 agent 看到完全相同的搜索结果。

**H 的设计**：在 Phase 1 开始前，先用一个专用 agent 从搜索结果中提取结构化事实表（指标名、值、年份、口径、来源），写入 SharedMemory。后续 agent 必须引用此事实表中的值。

## 六、结论

### A-F 全部实施后的预期效果

| 指标 | 当前 | A-F 实施后 | 降幅 |
|------|------|-----------|------|
| 数据矛盾率 | 23.5% (16/68) | **2-3%** | ~90% |
| Prompt 泄漏 | 25% (2/8 agent) | **0%** | 100% |
| 数据重复率 | 75% | **~65%** | 仅 13% |
| 综合质量评分 | 6/10 | **8.5/10** | +2.5 |

### 诚实评估

1. **A-F 可以大幅改善数据矛盾**：从 23.5% 降至 2-3%，这是显著进步
2. **Prompt 泄漏可完全消除**：后处理扫描可以清除所有泄露
3. **数据重复仅能微弱改善**：需要额外的 G 方案（数据分配调度）
4. **LLM 编造风险无法归零**：这是生成式 AI 的结构性限制，A-F 后仍有 ~2-3% 的残余风险
5. **鲁棒性**：B+F 双层防线可以应对不同类型的报告（不限于财务分析），因为检测逻辑基于通用正则而非领域特定规则
