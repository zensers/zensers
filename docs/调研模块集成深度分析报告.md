## 2. 调研任务触发

### 2.1 触发入口

调研任务有两个主要触发路径：

**路径A：对话式触发** (`ResearchAPI.start_research`)
- 文件：`src/api/research_api.py:242-260`
- 流程：用户输入 → 语言检测 → 创建Session → ConversationStateMachine初始化 → 进入对话模式
- 状态机初始状态：`ConversationState.UNDERSTANDING`

**路径B：模板快速启动** (`ResearchAPI.quick_start`)
- 流程：用户选择预设模板 → 跳过对话阶段 → 直接进入框架确认或执行阶段
- 支持 `autoConfirm` 参数，可自动跳过确认直接执行

### 2.2 对话状态机

```
UNDERSTANDING → CLARIFYING → FRAMEWORK_CONFIRM → EXECUTING → PREVIEWING → COMPLETED
                                    ↕                    ↕
                                  PAUSED ←─────────────┘
                                    ↓
                                 CANCELLED
```

状态转换由LLM驱动的`_llm_converse`方法决定，LLM返回的`action`字段决定下一步行为：
- `continue_chat` → 继续对话
- `enter_framework` → 进入框架确认
- `modify_research` → 暂停并修改
- `resume_research` → 恢复执行
- `revise_report` → 进入报告修订
- `regenerate_report` → 重新生成报告
- `inject_requirement` → 注入新需求（不暂停）

### 2.3 工具调用循环

`_llm_converse`实现了多轮工具调用循环（最多10轮）：
1. LLM生成JSON响应（含可选`tool_call`字段）
2. 如有`tool_call`，执行对应工具（web_search/news_search/scrape_url/get_current_datetime）
3. 工具结果注入上下文，再次调用LLM
4. 循环直到LLM不再请求工具调用

### 2.4 集成点分析

| 集成点 | 位置 | 说明 |
|--------|------|------|
| SessionManager | `src/core/session_manager.py` | 管理会话生命周期、上下文存储 |
| ConversationStateMachine | `src/core/dialogue/state_machine.py` | 对话状态机，控制流程转换 |
| SmartClarifier | `src/core/orchestrator/smart_clarifier.py` | 智能追问，补充研究细节 |
| DialogueIntentState | `src/core/dialogue/dialogue_intent_state.py` | 对话意图状态跟踪 |
| CancelManager | `src/core/orchestrator/execution/coordinator/cancel_manager.py` | 暂停/取消/恢复控制 |

## 3. 调研问卷设计

### 3.1 问卷数据模型

文件：`src/survey/models.py`

**核心模型层次：**

```
Survey
├── survey_id: str
├── title: str
├── description: str
├── questions: List[Question]
│   ├── question_id: str
│   ├── text: str
│   ├── question_type: QuestionType (11种题型)
│   ├── options: List[QuestionOption]
│   ├── required: bool
│   ├── validation_rules: Dict
│   └── skip_logic: Dict (条件跳转逻辑)
├── created_at / updated_at
└── metadata: Dict
```

**支持的11种题型：**
1. `single_choice` - 单选
2. `multiple_choice` - 多选
3. `likert` - 李克特量表
4. `open_ended` - 开放题
5. `yes_no` - 是否题
6. `ranking` - 排序题
7. `matrix` - 矩阵题
8. `scale` - 量表评分
9. `dropdown` - 下拉选择
10. `date_time` - 日期时间
11. `file_upload` - 文件上传

### 3.2 条件跳转逻辑 (Skip Logic)

Question模型支持`skip_logic`字段，实现条件显示/隐藏：

```python
skip_logic = {
    "depends_on": "q_1",        # 依赖的问题ID
    "condition": "equals",       # 条件类型
    "value": "Yes",              # 条件值
    "effect": "show"             # 效果：show/hide
}
```

支持的条件类型：`equals`, `not_equals`, `in`, `greater_than`, `less_than`

### 3.3 问卷创建流程

**API端点：** `POST /api/v1/surveys` (`src/survey/task_api.py:63-73`)

流程：
1. 前端提交 `CreateSurveyRequest` (title + description + questions)
2. `SurveyClient.create_survey()` 解析问题列表，构建Survey对象
3. 生成 `survey_id`，返回问卷元数据

**前端入口：** `/surveys/new` 页面
- 提供JSON编辑器，默认模板包含3个示例问题
- 调用 `api.createSurvey()` 提交

### 3.4 问卷设计审查

当前系统中问卷审查为**隐式审查**，通过以下机制实现：

1. **数据验证**：Question模型的`required`字段和`validation_rules`提供基础验证
2. **Skip Logic验证**：`Survey.get_visible_questions()` 方法验证跳转逻辑的一致性
3. **前端预览**：`/surveys/[id]` 页面展示问题列表，供设计者检查

**缺失的审查环节：**
- 无正式的问卷审查工作流（如多人审核、审查状态标记）
- 无问卷逻辑一致性自动校验
- 无题目间矛盾检测

## 4. 问卷分发

### 4.1 分发架构

采用**策略模式**，通过Backend抽象层支持多种分发渠道：

```
SurveyBackend (ABC)
├── TencentSurveyBackend   # 腾讯问卷API
├── AISimulationBackend    # AI模拟受访者
└── MockSurveyBackend      # 测试用Mock
```

**Backend工厂** (`src/survey/backends/factory.py`)：
- 自动注册：模块加载时通过`_auto_register()`注册所有内置后端
- 单例管理：`get_or_create()` 提供缓存的单例实例
- 线程安全：使用`threading.Lock`保护注册和实例化

### 4.2 腾讯问卷分发

文件：`src/survey/backends/tencent_survey.py`

**能力矩阵：**
| 能力 | 支持 |
|------|------|
| 配额控制 | ✓ |
| 暂停/恢复 | ✗ |
| Webhook回调 | ✓ |
| 实时状态 | ✓ |
| 激励设置 | ✗ |

**分发流程：**
1. `create_survey()` → 调用腾讯API创建问卷，返回external_id
2. `distribute()` → 获取问卷URL（腾讯问卷创建后自动可访问）
3. 返回share_url供分发

**配置集成：**
- 支持从`settings.platforms.tencent_survey`读取配置
- 支持环境变量覆盖

### 4.3 AI模拟分发

文件：`src/survey/backends/ai_simulation.py`

**能力矩阵：**
| 能力 | 支持 |
|------|------|
| 配额控制 | ✗ |
| 暂停/恢复 | ✓ |
| Webhook回调 | ✗ |
| 实时状态 | ✓ |
| 激励设置 | ✓ |

**分发流程：**
1. 从`DistributionConfig.sampling_spec`提取模板和人物类型
2. 创建`SimulationExecutor`，执行AI模拟
3. 生成Personas → 模拟回答 → 收集Responses
4. 持久化结果到SQLite（SurveyResponseStore + SurveyPersonaStore）
5. 返回模拟任务ID

### 4.4 分发配置模型

```python
DistributionConfig:
    target_count: int                    # 目标样本数
    quota: Optional[QuotaConfig]         # 配额控制
    incentive: Optional[float]           # 激励金额
    deadline: Optional[datetime]         # 截止时间
    channels: List[str]                  # 分发渠道
    sampling_spec: Optional[Dict]        # AI模拟采样规格
```

### 4.5 SurveyTask生命周期

```
DRAFT → PENDING → ACTIVE → COMPLETED
                 ↕        ↕
               PAUSED   WAITING → TIMEOUT
                          ↓
                       FAILED / CANCELLED
```

**Phase 9扩展字段：**
- `parent_task_id` - 关联主研究任务ID
- `parent_phase` - 关联阶段（如DATA_COLLECTION）
- `expected_completion_date` - 预期完成日期
- `timeout_days` / `timeout_action` - 超时配置
- `callback_topic` - 完成时通过MessageBus发布的事件主题
- `polling_enabled` / `polling_interval_hours` - 轮询配置（当Webhook不可用时）

## 5. 问卷收集与Webhook

### 5.1 Webhook处理器

文件：`src/survey/webhook_handler.py`

**支持的事件类型：**
| 事件 | 处理逻辑 |
|------|----------|
| `answer.create` | 新回答提交 → 更新collected_count |
| `survey.complete` | 问卷完成 → 获取全部结果 → PII加密 → 存储SharedMemory → 发布MessageBus事件 |
| `survey.timeout` | 问卷超时 → 更新状态为TIMEOUT → 发布超时事件 |
| `quota.reached` | 配额达标 → 发布配额达标事件 |

### 5.2 安全机制

| 机制 | 实现 |
|------|------|
| HMAC签名验证 | `sha256=`格式签名，常量时间比较防时序攻击 |
| 时间戳防重放 | 最大漂移300秒（5分钟） |
| PII数据加密 | Fernet对称加密（AES-128-CBC），降级为HMAC伪加密 |
| 速率限制 | 滑动窗口算法，默认100请求/60秒 |
| 授权验证 | 验证Webhook对应有效任务，拒绝已完成/失败任务的回调 |
| 载荷大小限制 | 最大1MB |
| 重放检测 | webhook_id去重 |

### 5.3 外部ID索引

为优化Webhook处理性能，维护`(backend_type, external_id) → task_id`索引：
- 首次查询时构建索引（延迟初始化）
- 索引未命中时回退到全表扫描
- 支持强制重建索引（`rebuild_index()`）

### 5.4 数据收集存储

**存储层** (`src/survey/stores.py`)：

| Store | 表名 | 用途 |
|-------|------|------|
| SurveyTaskStore | survey_tasks | 任务元数据和进度 |
| SurveyResponseStore | survey_responses | 问卷回答数据 |
| SurveyPersonaStore | survey_personas | AI人物设定数据 |
| SurveyCheckpointStore | survey_checkpoints | 任务恢复检查点 |

所有Store共享`knowledge_bank.db`数据库，通过`ConnectionManager`管理连接。

## 6. AI模拟引擎

### 6.1 模拟执行流程

文件：`src/survey/engine/simulation_engine.py`

```
SimulationExecutor.execute()
    │
    ├── Phase 1: Pre-flight Check
    │   └── 验证LLM可用性、配置完整性
    │
    ├── Phase 2: Generate Personas
    │   ├── PersonaGeneratorV2.generate_batch()
    │   │   ├── 尝试LLM生成（并发控制，max_concurrent=5）
    │   │   └── 失败回退到规则生成
    │   └── 返回 personas + generation_stats
    │
    ├── Phase 3: Simulate Survey
    │   ├── _simulate_all()（并发控制，max_concurrent=10）
    │   │   └── _simulate_persona() → 逐题回答
    │   │       ├── 检查skip_logic
    │   │       ├── _answer_question()
    │   │       │   ├── LLM模式：构建Prompt → 调用LLM → 解析响应
    │   │       │   └── 规则模式：随机选择选项
    │   │       └── 记录回答历史
    │   └── 返回 responses
    │
    └── 生成 cost_report
```

### 6.2 人物模板系统

文件：`src/survey/engine/persona_templates.py`

**12个中文模板（6消费者 + 6专家）：**

| 消费者模板 | 专家模板 |
|-----------|---------|
| 一线白领 (25-40, 一线城市, 高收入) | 行业分析师 (30-55, 市场研究背景) |
| 二三线家庭 (30-50, 家庭导向) | 企业高管 (40-60, 战略视角) |
| 下沉市场用户 (25-55, 价格敏感) | 技术专家 (30-50, 技术权威) |
| Z世代学生 (18-24, 社交驱动) | 政策研究员 (30-55, 政策分析) |
| 高净值人群 (35-60, 品质优先) | 一线从业者 (25-45, 行业实践) |
| 银发族 (60-80, 健康导向) | 学术研究者 (30-60, 方法论严谨) |

**6个英文多国模板：**
- `us_urban_professional` / `us_suburban_family` (美国)
- `european_urban_consumer` (欧洲)
- `japan_urban_consumer` (日本)
- `global_industry_analyst` / `global_tech_expert` (全球专家)

**一致性约束规则：**
- 收入 ↔ 价格敏感度映射
- 年龄 ↔ 数字素养映射
- 专家人物 → 低价格敏感度

### 6.3 Prompt构建器

文件：`src/survey/engine/prompt_builder.py`

**4级Prompt层次：**

| 级别 | 内容 | 适用场景 |
|------|------|----------|
| MINIMAL | 基础人口统计 | 快速模拟 |
| STANDARD | MINIMAL + 性格特质 | 标准模拟 |
| ENHANCED | STANDARD + 回答历史 | **默认**，保持一致性 |
| FULL | ENHANCED + 背景故事 + 决策特征 | 高保真模拟 |

**温度调度：** 不同题型使用不同temperature
- 是否题：0.2（最确定）
- 单选/多选：0.3
- 量表/排序：0.4
- 开放题：0.8（最发散）

### 6.4 成本监控

文件：`src/survey/engine/cost_monitor.py`

- `LLMCostTracker` - 跟踪每次LLM调用的token数和成本
- `RetryHandler` - 指数退避重试（最多3次，超时30秒）
- 预算限制：默认$5.0，超出抛出`BudgetExceededError`

### 6.5 校准与验证

文件：`src/survey/engine/calibrator.py`

**校准流程：**
1. 加载基准数据（如World Values Survey）
2. 计算模拟分布与基准分布的相似度（Jensen-Shannon散度）
3. 计算方差比（模拟方差/人类方差，理想值≈1.0）
4. 计算分布重叠系数
5. 子群分析（consumer/expert/under_35/over_50）
6. 偏差检测（分布偏移/响应同质化/过度方差/质量不一致）
7. 生成调优建议

## 7. 统计分析

### 7.1 描述性统计

文件：`src/survey/analysis/descriptive.py`

**分析能力：**

| 题型 | 统计指标 |
|------|----------|
| 单选/是否/下拉 | 频次分布、百分比、最常选项 |
| 多选 | 频次分布、总选择次数、人均选择数 |
| 量表/Likert | 均值、中位数、标准差、最小/最大、分布 |
| 开放题 | 回答数、平均/最小/最大长度、样本文本 |
| 排序题 | 各排名位置的频次分布 |
| 矩阵题 | 各行各列的频次分布 |

**整体统计：** 完成率、平均/中位回答时长

### 7.2 情感分析

文件：`src/survey/analysis/sentiment.py`

**双语支持（中文+英文）：**
1. 自动语言检测
2. 分词：中文用jieba，英文用正则
3. 词典查找：正面词/负面词/强化词/否定词
4. 否定翻转：否定词翻转后续情感词极性
5. 强化词乘数：调整情感强度
6. 中文子词匹配：对未命中词典的长词进行子词拆分匹配
7. LLM增强：低置信度文本（<0.4）可选LLM重新分析

### 7.3 交叉分析

文件：`src/survey/analysis/crosstab.py`

- 自动发现值得交叉分析的题目对（最多3对）
- 生成交叉频次表
- 卡方检验（χ²统计量、p值、显著性判断）

### 7.4 词云生成

文件：`src/survey/analysis/wordcloud.py`

- 从开放题回答中提取关键词
- 生成频次统计
- 可选生成词云图片（PNG格式）

### 7.5 统计检验

文件：`src/survey/analysis/stats_tests.py`

- 提供假设检验工具函数
- 支持卡方检验等常用统计检验

### 7.6 响应质量验证

文件：`src/survey/services/response_quality_validator.py`

**7种质量问题检测：**

| 问题类型 | 检测逻辑 | 严重度权重 |
|----------|----------|-----------|
| straight_line | 单选题答案相同比例≥70% | high:0.3 |
| speeder | 回答时长<30秒 | high:0.3 |
| incomplete | 缺失必答题 | high:0.3 |
| inconsistent | 逻辑矛盾 | medium:0.15 |
| nonsense_text | 匹配无意义模式（纯字母/数字/键盘乱敲/过短） | medium:0.15 |
| pattern_response | 答案呈单调递增/递减模式 | medium:0.15 |
| logic_error | 违反问卷逻辑规则 | low:0.05 |

**质量评分计算：** `score = max(0, 1 - Σ(severity_weight))`

## 8. 报告生成

### 8.1 问卷分析报告

文件：`src/survey/analysis/report_builder.py`

**SurveyReportBuilder.build() 流程：**
1. 描述性统计 → `DescriptiveAnalyzer.analyze()`
2. 收集开放题文本

4. 词云生成 → `WordCloudGenerator.generate()`

### 8.2 研究报告生成

研究报告的生成由`ResearchOrchestrator`驱动，经过多阶段执行：

**执行器** (`src/api/research_executor.py`)：

```
ResearchExecutor.execute()
    │
    ├── 暂停/取消检查
    ├── 初始化ResearchOrchestrator
    ├── 提取研究参数（topic, framework, sections）
    ├── 用户偏好路由（Level D: focus_areas映射）
    ├── 进度跟踪初始化
    │
    ├── orchestrator.research()
    │   ├── 阶段1: 信息搜集 (Web Search + News + Scraping)
    │   ├── 阶段2: 数据分析 (各Agent并行执行)
    │   ├── 阶段3: 内容合成 (Section生成)
    │   └── 阶段4: 质量检查
    │
    ├── 处理待注入需求 (_process_pending_injects)
    ├── 状态机转换 → COMPLETED
    ├── 复制预览文件
    └── 推送完成消息
```

### 8.3 内容编排

文件：`src/content/content_orchestrator.py`

**ContentOrchestrator** 负责将研究结果转换为结构化HTML：

**支持格式：** docx, pptx, pdf, html, research_report

**HTML中间格式：**
- Word: `<article><section>...</section></article>`
- PPT: `<section class="slide" data-type="...">...</section>`

**核心处理：**
1. 解析Sections（`_parse_sections`）
   - Markdown标题提取（`_parse_markdown_title`）避免重复
   - 递归解析子章节（最大深度10层）
   - 章节去重（`_dedup_sections`）：相同title保留最佳版本
2. 模板渲染
   - 加载HTML模板（`TemplateEngine.load_template()`）
   - 注入变量（title, sections, charts, tables, key_findings等）
   - 图表处理：HTML模式用base64嵌入，输出目录模式用外部文件
3. Markdown→HTML转换（`_content_to_html`）
   - 支持标题、表格、图片、列表等
   - Markdown表格自动转换为HTML表格

**SectionType分类：**
- `BODY` - 正文分析章节
- `EXECUTIVE_SUMMARY` - 执行摘要
- `CONCLUSION` - 研究结论
- `APPENDIX` - 附录
- `DATA_SOURCE` - 数据来源

## 9. 报告合并

### 9.1 章节合并机制

报告合并在两个场景下发生：

**场景A：增量注入合并** (`ResearchExecutor._process_pending_injects`)

当研究执行期间用户注入新需求（`inject_requirement`），系统：
1. 提取待注入操作（add_section / cancel_section / merge_requirement / revise）
2. 对add/merge操作：
   - 使用`IntelligentRoutingAdapter`分析增量路由
   - 创建新`ResearchOrchestrator`执行增量研究
   - 合并结果：新章节追加到原有sections列表
3. 对revise操作：
   - 使用`RevisionService.revise_from_user_feedback()`修改指定章节

**合并策略：**
```python
merged_sections = list(original_sections)
for s in inject_sections:
    if s.get("id") not in [x.get("id") for x in merged_sections]:
        merged_sections.append(s)  # 仅追加不重复的章节
```

**场景B：内容编排去重** (`ContentOrchestrator._dedup_sections`)

在HTML渲染阶段，对相同title的章节进行去重，保留优先级最高的版本：
- 内容非空 > 空内容
- 非结构化标记开头 > 结构化标记开头
- 内容更长 > 内容更短
- CONCLUSION类型 > BODY类型

### 9.2 缺失的合并功能

当前系统**缺少**正式的多报告合并功能：
- 无多份独立研究报告的合并工作流
- 无章节冲突解决策略（当两份报告有相同主题章节时）
- 无数据对齐和一致性检查

## 10. 报告修订

### 10.1 修订系统架构

报告修订通过`ResearchAPI`的对话式交互实现：

**修订触发：**
- LLM返回`action="revise_report"`时触发
- 用户在研究完成后提出修改请求

**修订流程（V2修订系统）：**

```
_handle_v2_revision()
    │
    ├── 分析用户修订意图
    │   ├── RevisionIntentMapper: 映射意图到修订类型
    │   ├── RevisionTypeInferrer: 推断修订类型
    │   └── CascadeUpdateAnalyzer: 分析级联更新影响
    │
    ├── 定位修订目标
    │   └── EnhancedSectionLocator: 精确定位目标章节
    │
    ├── 生成修订任务流
    │   └── 创建多步骤修订任务（preview → confirm → apply）
    │
    └── 执行修订
        ├── RevisionService.revise_from_user_feedback()
        └── 更新报告内容
```

### 10.2 修订类型

系统支持以下修订类型：
- **section** - 单章节修订
- **full** - 全文修订

### 10.3 级联更新分析

`CascadeUpdateAnalyzer` 分析修订一个章节对其他章节的影响：
- 数据引用检查：被修订章节的数据是否被其他章节引用
- 逻辑一致性检查：修订是否破坏章节间的逻辑关系
- 建议受影响的章节同步更新

### 10.4 修订确认流程

```
用户提出修订请求
    ↓
生成修订预览 (Preview)
    ↓
用户确认 (y/n)
    ↓ 确认
应用修订 → 更新报告
    ↓ 拒绝
保持原报告不变
```

## 14. 集成问题与改进建议

### 14.1 当前集成缺陷

| 编号 | 缺陷 | 严重度 | 说明 | 核实结果 |
|------|------|--------|------|----------|
| D1 | 问卷与研究Orchestrator的集成为同步阻塞式 | 中 | **原描述不准确，已修正。** 实际上ResearchOrchestrator已通过`_execute_survey_integration()`调用`SurveyIntegrationAgent`，问卷结果会注入`results_for_aggregation`。但该调用是同步阻塞的——在`_perform_research()`中await等待问卷完成才继续后续阶段，对于第三方平台（腾讯问卷）的长周期收集（3-7天），会阻塞整个研究流程。 | **已修正**：耦合存在但方式不理想 |
| D2 | 无正式问卷审查工作流 | 中 | `SurveyIntegrationAgent`的third_party_workflow中有`create_survey`步骤，但无审查/审批环节。`_auto_generate_questions()`自动生成题目后直接进入分发，缺少人工审核确认。 | **确认准确** |
| D3 | 无多报告合并功能 | 中 | `ResearchExecutor._process_pending_injects`仅支持增量注入合并（追加新章节），不支持两份独立研究报告的章节级智能合并（冲突检测、数据对齐）。 | **确认准确** |
| D4 | Webhook签名验证在无secret时正确拒绝 | 低 | **原描述不准确，已修正。** 代码`_verify_signature()`在`enable_signature_verification=True`且无secret时，会`return False`拒绝请求（line 382-385），这是正确安全行为。但`enable_signature_verification`默认为True，开发环境需显式设为False才能跳过验证。 | **已修正**：安全行为正确，但开发体验可改善 |
| D5 | 第三方问卷结果需等待Webhook回调，无主动轮询调度器 | 中 | **原描述不准确，已修正。** AI模拟结果在`AISimulationBackend.distribute()`内同步完成并持久化，不存在回流问题。但腾讯问卷后端依赖Webhook回调，虽然`SurveyTask`模型有`polling_enabled`/`polling_interval_hours`字段，系统缺少主动轮询调度器来定期检查未完成的WAITING状态任务。 | **已修正**：AI模拟回流正常，第三方缺轮询调度 |
| D6 | 校准数据依赖外部文件 | 低 | `SimulationCalibrator._load_benchmark()`在文件不存在时抛出`CalibrationDataMissingError`，设计为Fail Fast。但缺少内置示例数据或数据生成引导。 | **确认准确** |
| D7 | 前端问卷编辑器简陋 | 中 | `/surveys/new`页面仅提供JSON文本编辑器，无可视化拖拽设计器、题目预览、逻辑设置面板。 | **确认准确** |
| D8 | 无问卷版本管理 | 低 | 问卷修改后无版本记录，Survey模型有`updated_at`但无版本号或变更历史。 | **确认准确** |

### 14.2 改进建议

**P0 - 关键集成（问卷↔研究执行模式优化）：**
1. 将`_execute_survey_integration()`改为异步非阻塞：创建SurveyTask后立即返回，研究流程继续执行其他不依赖问卷数据的章节
2. 通过MessageBus订阅`survey.completed`事件，在问卷完成时触发依赖问卷数据的分析章节
3. 实现轮询调度器：定期扫描`WAITING`状态的SurveyTask，调用Backend的`get_status()`检查进度

**P1 - 问卷审查：**
1. 在`SurveyIntegrationAgent`中增加审查步骤：`create_survey → review_survey → distribute`
2. 实现Skip Logic一致性自动校验
3. 支持多人审核（审核人分配、审核意见、审核通过/驳回）

**P2 - 报告合并：**
1. 实现多报告合并工作流
2. 章节冲突检测与解决策略（保留最新/人工选择/智能合并）
3. 数据对齐检查（相同指标在不同报告中的数值一致性）

**P3 - 前端体验：**
1. 可视化问卷设计器（拖拽题型、实时预览、逻辑设置）
2. 问卷进度实时仪表盘
3. 分析报告交互式图表（可下钻、可筛选）

**P4 - 质量保障：**
1. AI模拟结果与真实数据的自动校准
2. 模拟置信度标注（每个回答标注置信水平）
3. 异常值自动检测与标记
