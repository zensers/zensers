## 2. 根因链

### 2.1 DAG 阶段分离被绕过

系统设计了完整的 5 阶段 DAG 架构（`src/core/decomposition/strategies.py:250-256`）：

```
DATA_COLLECTION → DATA_VALIDATION → DEEP_ANALYSIS → SYNTHESIS → REPORT_GENERATION
```

`IndustryResearchStrategy.decompose()` 能正确生成每个阶段独立的 AgentSpec，包含：
- DATA_COLLECTION：8 个 agent，`dependencies=[]`，skills 包含 `search_skill`
- DATA_VALIDATION：8 个 agent，`dependencies=[对应的DC agent]`，skills 只有 `llm_skill`
- DEEP_ANALYSIS：8 个 agent，`dependencies=[对应的Validation agent]`，skills 不含 `search_skill`
- SYNTHESIS：依赖章节的 agent，`dependencies=[所有Analysis agent]`
- REPORT_GENERATION：1 个 agent

**但 BYD 报告实际执行情况完全不同。**

### 2.2 BYD 报告实际走的路径

从 `research_8c6675c2.json` 的实际数据看：

```json
{
  "agent_id": "phase_1_agent_0",
  "depends_on": [],
  "category": "analysis",
  "data_points_count": 531
}
```

**全部 8 个 agent 的特征：**

| 字段 | 实际值 | 应有值（如果走 DAG） |
|------|--------|---------------------|
| agent_id | `phase_1_agent_N`（全在 phase_1） | 应有 `data_collection_N`, `validation_N`, `deep_analysis_N` 等 |
| depends_on | `[]`（全部无依赖） | Validation 应依赖 DC，Analysis 应依赖 Validation |
| category | 全部 `"analysis"` | 应有 `research`, `quality-check`, `market-analysis`, `synthesis` 等 |
| data_points_count | 531（每个 agent 拿到全量） | DC agent 应收集数据，Analysis agent 应只拿过滤后的数据 |

**结论：8 个 agent 全部在一个批次并行执行，DAG 的 5 阶段分离完全没有生效。**

### 2.3 为什么 DAG 没生效

代码中有两个分流点（`orchestrator.py`）：

**分流点 1：decompose 失败（line 700-714）**

```python
decomposition_plan = None
try:
    strategy = get_strategy(output_type_value)
    decomposition_plan = strategy.decompose(requirement, intent_result, framework_config)
except Exception as e:
    logger.warning(f"[{task_id}] Task decomposition failed, using default scheduling: {e}")
    decomposition_plan = None  # ← 降级为无 DAG
```

**分流点 2：create_agents_from_plan 失败（line 723-738）**

```python
if decomposition_plan:
    try:
        agents = self._create_agents_from_plan(decomposition_plan, ...)
    except Exception as e:
        logger.warning(f"[{task_id}] Failed to create Agents by plan, falling back: {e}")
        agents = self._create_agents(requirement, ...)  # ← 降级为综合 agent
```

两个分流点的 fallback 都指向同一个方法：`_create_agents()`。

### 2.4 _create_agents() 的设计决策

`orchestrator.py:3762-3793`：

```python
# normal 章节（research_ 前缀）是综合研究 Agent（数据收集+分析一体），
# 应使用 "analysis" 让 generic_agent 走 DEEP_ANALYSIS 分支

# === 不再创建独立的数据收集Agent和分析Agent ===
# 之前的实现为每种数据类型创建独立Agent，导致Agent数量爆炸
# 现在改为每个章节一个综合Agent，减少Agent数量和搜索请求
```

这是一个**性能优化**的决策：把 DC + Analysis 合并为一个综合 agent，代价是丧失了阶段间的数据核对机会。

### 2.5 完整的因果链

```
性能优化（减少 agent 数量）
  → _create_agents() 合并 DC + Analysis 为单一综合 agent
  → 所有 agent 在同一批次并行（depends_on=[]）
  → 无中间阶段，无法做数据核对和统一
  → 每个综合 agent 独立搜索，各自拿到不同来源的同名指标值
  → engine.py:2095 全量注入 data_points（每个 agent 拿到 531 个数据点）
  → 8 个 agent 基于不同数据源独立写报告
  → 同一指标出现不同数值（矛盾率 23.5%）
  → 无统一规范数据约束（canonical_data 注入是软约束，LLM 可忽略）
  → 结果：报告数据矛盾
```

## 3. 系统已有的数据统一机制及其局限

### 3.1 规范数据注册表（Canonical Registry）

**位置**：`engine.py:1049-1059, 1313-1343`

**流程**：
1. 批次执行后，`MetricExtractor` 从 agent 返回的 `data_points` 提取指标
2. 写入 `_canonical_registry` → `_active_canonical_data`
3. 广播到 `SharedMemory("_canonical_registry")`
4. 后续 agent 通过 `task["canonical_data"]` 获取

**局限**：
- 所有 agent 在同一批次 → canonical data 在**批次结束后**才提取 → 同批次 agent 之间无法共享
- `generic_agent.py:467-476` 注入 prompt 是软约束："优先使用这些值"，LLM 经常忽略

### 3.2 Agent 间 SharedMemory 实时更新

**位置**：`generic_agent.py:477-492`

```python
# Final SharedMemory check before LLM call: pick up last-millisecond resolution
_sm_latest = self._shared_memory.get("_canonical_registry", {})
if _sm_latest and _sm_latest != canonical_data:
    _diff = {k: v for k, v in _sm_latest.items() if k not in canonical_data or ...}
    if _diff:
        prompt += f"\n\n## 实时更新规范数据（其他agent已完成）\n{_ds}\n"
```

**局限**：
- 8 个 agent 并行执行，启动时间几乎相同
- SharedMemory 中没有数据（还没 agent 完成）
- 这段代码在并行场景下基本无效

### 3.3 聚合阶段冲突检测

**位置**：`result_aggregator.py:1048-1078`

**实际行为**：
- 只比较 `agent_id` 这个 key（检查"两个 agent 是否写了同一个 key"）
- **完全不解析文本内容去核对数字**
- "销量 380 万" vs "销量 460 万" 这种矛盾无法检测

### 3.4 小结：三层防线全部失效

| 防线 | 机制 | 失效原因 |
|------|------|----------|
| 预防：canonical data 共享 | SharedMemory + prompt 注入 | 同批次并行，数据来不及共享；prompt 是软约束 |
| 预防：prompt 引用规范 | "优先使用这些值" | LLM 可忽略，非强制 |
| 检测：聚合冲突检测 | result_aggregator 按 key 比较 | 只比较 agent_id，不解析内容 |

## 4. 系统中 DAG 架构的详细设计

### 4.1 分解策略（IndustryResearchStrategy）

`strategies.py:242-420` 定义了完整的 5 阶段分解：

**Phase 1: DATA_COLLECTION**（8 个 agent）
- skills: `["search_skill", "news_search", "llm_skill"]`
- dependencies: `[]`
- 职责：纯搜索和数据收集

**Phase 2: DATA_VALIDATION**（8 个 agent）
- skills: `["llm_skill"]`
- dependencies: `[对应的 DC agent]`
- 职责：交叉验证数据准确性和完整性

**Phase 3: DEEP_ANALYSIS**（8 个 agent）
- skills: 按 aspect 分配（`["llm_skill", "data_analysis"]` 等，不含 search_skill）
- dependencies: `[对应的 Validation agent]`
- 职责：基于已验证的数据做深度分析

**Phase 4: SYNTHESIS**（N 个 agent，用于依赖章节）
- dependencies: `[所有 Analysis agent]`
- 职责：综合各章节分析结果

**Phase 5: REPORT_GENERATION**（1 个 agent）
- 职责：生成最终报告

### 4.2 调度器（Scheduler）

`scheduler.py` 支持两种调度方式：
- `schedule_from_decomposition()`：按 DecompositionPlan 的 AgentSpec 依赖关系生成批次
- `schedule_from_agents()`：按 agent 的 `depends_on` 生成批次

**关键**：如果 decomposition_plan 正确传递，调度器会生成 5 个批次，批次间串行执行。此时 Phase 2 可以拿到 Phase 1 的数据，Phase 3 可以拿到 Phase 2 的验证结果。

### 4.3 _create_agents_from_plan() vs _create_agents()

| | `_create_agents_from_plan()` | `_create_agents()` |
|---|---|---|
| 触发条件 | decomposition_plan 成功 | fallback |
| agent 数量 | 每章节 3-4 个（DC+Validation+Analysis+Synthesis） | 每章节 1 个综合 agent |
| 阶段分离 | 有（5 阶段 DAG） | 无（单批次并行） |
| depends_on | 按依赖链设置 | 全部 `[]` |
| 数据核对机会 | Phase 1→2 之间可以做 | 没有 |

## 7. 解决方向（待讨论）

### 方向 A：恢复 DAG 阶段分离

让报告走 `_create_agents_from_plan()` 路径，确保每章节有独立的 DC 和 Analysis agent。在 Phase 1（DC）和 Phase 3（Analysis）之间插入数据核对环节。

**优点**：从架构层面解决问题，canonical data 在阶段间自然传播
**风险**：Agent 数量增加（8 章节 × 3 阶段 = 24+ agent），执行时间增加
**待解决**：需要确定 BYD 为什么没走这条路，修复分流点

### 方向 B：保持当前单 agent 架构，在聚合阶段深度对账

不改 agent 调度，保持每章节 1 个综合 agent。在聚合阶段引入 DataReconciler，用 LLM 辅助做语义级数据对账。

**优点**：不改调度架构，风险低
**缺点**：是事后补救，不是事前预防；LLM 对账成本高

### 方向 C：混合方案

保持当前 agent 创建方式，但在 engine 的批次执行中插入"数据核对"步骤：
1. 所有综合 agent 执行完成后、聚合之前
2. engine 提取所有 agent 输出中的指标
3. 交叉核对，生成统一的 canonical data
4. 触发一轮"修订"——让 agent 基于统一数据修正输出

**优点**：不增加 agent 数量，利用现有 canonical data 基础设施
**缺点**：需要额外的 LLM 调用来做修订
